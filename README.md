# Smart Office AI Agent

AI-ассистент для поиска и бронирования переговорных. Пользователь задаёт параметры встречи в чате, а агент обращается к Java-инструментам для поиска свободных комнат и работы с бронированиями в PostgreSQL. Сохранение бронирования требует отдельного подтверждения пользователя.

## Возможности

- Поиск свободных переговорных по вместимости и временному интервалу.
- Подготовка, подтверждение и отмена ожидающего бронирования.
- Просмотр подтверждённых бронирований сотрудника.
- История диалога, разделённая по `sessionId`.
- Ответы по правилам офиса через опциональный RAG.
- Веб-интерфейс и REST API.

## Технологии

Java 21 · Spring Boot 3.5.14 · LangChain4j · GigaChat · Spring Data JPA · PostgreSQL 16 · Liquibase · Maven · Docker Compose

Для интеграции с GigaChat используется `chat.giga:langchain4j-gigachat:0.1.22`. Тесты написаны на JUnit 5, Mockito и AssertJ.

## Быстрый запуск

Для запуска в Docker нужны Docker Compose и Authorization Key GigaChat API. Приложение использует scope `GIGACHAT_API_PERS`.

1. Клонируйте репозиторий:

   ```bash
   git clone https://github.com/dpnevsky/smart-office-ai-agent.git
   cd smart-office-ai-agent
   ```

2. Создайте файл окружения:

   ```bash
   cp .env.example .env
   ```

   В PowerShell:

   ```powershell
   Copy-Item .env.example .env
   ```

3. Укажите Authorization Key в `.env`:

   ```dotenv
   GIGACHAT_AUTH_KEY=your_authorization_key
   ```

   Нужен Authorization Key, а не временный access token. `.env` исключён из Git.

4. Запустите приложение и PostgreSQL:

   ```bash
   docker compose --profile full up --build
   ```

Веб-интерфейс доступен на [localhost:8080](http://localhost:8080), проверка состояния — на [/actuator/health](http://localhost:8080/actuator/health). Liquibase автоматически создаёт схему, пять переговорных и пример бронирования. Данные PostgreSQL сохраняются в Docker volume.

### Запуск через Maven

Для локального запуска приложения нужны JDK 21 и Maven. PostgreSQL можно запустить через Compose:

```bash
docker compose up -d postgres
```

Передайте ключ в окружение процесса и запустите приложение.

Bash:

```bash
export GIGACHAT_AUTH_KEY='your_authorization_key'
mvn spring-boot:run
```

PowerShell:

```powershell
$env:GIGACHAT_AUTH_KEY = 'your_authorization_key'
mvn spring-boot:run
```

При запуске из IDE задайте переменные в конфигурации запуска. Файл `.env` используется Docker Compose; приложение при запуске через Maven автоматически его не читает.

## Конфигурация

При запуске в Docker задавайте параметры в `.env`, при запуске через Maven или IDE — в окружении процесса.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `GIGACHAT_AUTH_KEY` | — | Authorization Key GigaChat API |
| `GIGACHAT_MODEL` | `GigaChat-Pro` | Модель для диалога и вызова инструментов |
| `GIGACHAT_VERIFY_SSL` | `false` | Проверка TLS-сертификатов GigaChat |
| `RAG_ENABLED` | `false` | Поиск контекста в правилах офиса |

В текущей конфигурации проверка TLS отключена. Для подключения с проверкой сертификатов настройте доверенные сертификаты в окружении Java и установите `GIGACHAT_VERIFY_SSL=true`.

При запуске через Maven доступны также `DB_URL`, `DB_USER`, `DB_PASSWORD` и `SERVER_PORT`. По умолчанию приложение подключается к `jdbc:postgresql://localhost:5432/smartoffice` с пользователем и паролем `smartoffice` и слушает порт `8080`. В Compose параметры подключения к БД заданы для контейнера `postgres`.

## Как работает бронирование

1. Агент вызывает `findFreeRooms` и получает свободные комнаты из базы данных.
2. `requestRoomBooking` сохраняет ожидающее бронирование для текущей сессии на 10 минут.
3. Пользователь подтверждает действие отдельным сообщением, например `Да, подтверждаю.`
4. Сервер проверяет подтверждение и разрешает вызов `confirmPendingBooking`.
5. `BookingService` проверяет пересечения с существующими бронированиями и сохраняет запись в PostgreSQL.

Проверка подтверждения выполняется в Java-коде. Без отдельного подтверждения инструмент сохранения недоступен модели, а сам инструмент дополнительно проверяет служебный параметр запроса. Ответ об успешном бронировании формируется по результату выполнения инструмента.

Пример диалога:

```text
Пользователь: Найди переговорную на 6 человек завтра с 14:00 до 15:00
             и забронируй на Ивана Петрова.
Ассистент:   Бронирование подготовлено. Подтвердите действие отдельным сообщением.
Пользователь: Да, подтверждаю.
```

Для просмотра бронирований можно отправить `Какие бронирования есть у Ивана Петрова?`. Отмена ожидающего бронирования удаляет подготовленное действие; отмена уже сохранённых бронирований не реализована.

## REST API

### Диалог

`POST /api/chat` · `Content-Type: application/json`

```json
{
  "sessionId": "office-session-1",
  "message": "Найди переговорную на 6 человек завтра с 14:00 до 15:00"
}
```

Формат ответа:

```json
{
  "sessionId": "office-session-1",
  "answer": "...",
  "executedTools": ["findFreeRooms"]
}
```

`sessionId` связывает сообщения одного диалога и ожидающее бронирование. `executedTools` содержит имена выполненных инструментов. Поля `sessionId` и `message` обязательны и не могут быть пустыми.

### Переговорные

`GET /api/rooms` возвращает список комнат с полями `id`, `name`, `floor`, `capacity` и `location`.

## Правила офиса и RAG

Для включения поиска по правилам установите `RAG_ENABLED=true` перед запуском приложения. При старте содержимое `src/main/resources/rag/office-rules.md` индексируется через GigaChat Embeddings. Найденный контекст передаётся модели при обработке вопросов о правилах офиса.

Индекс хранится в памяти и создаётся заново при перезапуске. При включённом RAG доступ к GigaChat требуется уже на этапе запуска.

## Структура проекта

```text
src/main/java/com/example/smartoffice/
├── ai/          # Интерфейс агента, инструменты и результаты операций
├── api/         # REST-контроллеры, DTO и обработка ошибок
├── config/      # GigaChat, память диалога, RAG и часы приложения
├── domain/      # Сущности переговорных и бронирований
├── repository/  # Доступ к PostgreSQL
└── service/     # Поиск комнат и управление бронированиями

src/main/resources/
├── db/changelog/  # Миграции Liquibase и начальные данные
├── rag/           # Правила офиса
└── static/        # Веб-интерфейс
```

`AgentConfig` связывает модель, инструменты и память диалога с окном в 20 сообщений. `ChatController` проверяет подтверждение пользователя, а `OfficeTools` вызывает сервисы приложения. Для интерпретации относительных дат агент получает текущую дату в часовом поясе `Europe/Moscow`.

## Тестирование

```bash
mvn test
```

Unit-тесты проверяют поиск комнат, срок жизни и отмену ожидающего бронирования, обработку подтверждений, доступность инструментов и обработку ошибок. Внешние зависимости в этих тестах заменены моками; PostgreSQL и ключ GigaChat для их запуска не нужны.

## Ограничения

История диалога и ожидающие бронирования хранятся в памяти одного процесса и теряются при перезапуске. Аутентификация пользователей не реализована; `sessionId` служит идентификатором диалога, а имя сотрудника передаётся в сообщении. Проверка пересечений бронирований выполняется в приложении и не защищена от одновременной записи пересекающихся интервалов на уровне базы данных. Правила из RAG используются как контекст для ответов и не являются ограничениями операций бронирования.
